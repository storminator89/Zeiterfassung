## What opens, and what remains authoritative

The former unconditional V5 `requireImplementedRuntime()` refusal is replaced
only for the canonical owner-private NEW Laravel cohort. The code **genuinely
admits a matching V5 Runtime**; describing all V5 PDO branches as unreachable is
no longer correct. There is no request bypass flag, unrestricted opener or V4
alias. Explicit default-off Runtime/FreshWeb/API selections still apply.

At every original source-identity boundary, the V5 cohort prerequisite checks
`application.sqlite` inside `chrono-fresh-<24 lowercase hex>`, private `0700` owner
and trusted ancestors, plus its original private `0600` single-link canonical
`runtime-admission.json`. Its bounded stable JSON must reconstruct the exact
immutable RuntimeAdmission. Database/directory/manifest identities and manifest
hash are captured on first physical check and compared for that Runtime object.
Replacement, aliases, malformed metadata and identity drift refuse.

This is an operator/owner-trust contract, **not cryptographic NEW-producer
provenance**, malicious same-UID/ABA protection or a persistent pin across process
restarts. The guard reads no key and is not authentication or human recovery.
Full details: [NEW cohort prerequisite](account-lifecycle-v5-new-runtime-cohort.md).

Existing PDO settings, header/WAL restrictions, complete four-row lineage ledger,
ordered application versions `[1, 2, 3, 4, 5]`, strictly typed intake policy and
final source-identity checks remain. The dedicated operation-scoped Writer still
requires current account/source/role/hash/generation authority under its sole
lock. Generationless V5 operations refuse. A failure after a commit attempt is
not reclassified as a confirmed rollback; no automatic retry is inferred.

The V5 Writer retains its V4 policy substrate internally, but public
`isIntakePolicyV4()` is never used to present V5 as V4. V2/V3/V4 flags, SQL,
settings and transaction lifecycles are unchanged.

## Minimal private NEW setup, not existing-data migration

Use the existing NEW-only producer and original stopped operator commands;
never rename/copy a database or rewrite a manifest to persuade admission.
Preparation itself creates no account/key, starts no server and enables no
Runtime flag. With API selected, the required order is:

1. NEW dormant V5 files in an existing private parent outside checkout/webroots.
2. Private App key and, if API is selected, NEW API signing key/metadata **while
   the source and login budget are empty, before any setup profile/token/user**.
3. Original short setup-token preparation; normal token/HTML/session/CSRF first
   Admin setup; deliberate monotone setup closure with requests stopped/drained.
4. Normal credential login and separately selected local Web/API operations.

The existing API-key CLI still requires Fresh/Runtime/Budget/API flags off.
FreshWeb still checks exact HTTPS origin/configuration, private encrypted
sessions, locks, CSRF and shared budget; its registrar requires either the exact
empty-source setup selection or a current structurally eligible local Admin.
That structural predicate does not prove that a human knows a usable password.
API requires its own physically admitted key and exact same Runtime/generation
composition, not metadata-only proof. [API contract](account-lifecycle-v5-api-composition.md).
LDAP/sync and terminal HTTP are not opened by this local profile.

New stored keys, tokens and account hashes require specific current operator
authority. They never belong in logs, source control or acceptance artifacts.
No previous test permission authorizes another persistent credential action.

- Nineteen credential-free physical Runtime cases and eight provider boundary

- Real first-Admin setup/closure, two authorized local accounts, normal login,
  role denial, correction approval by a different Admin, and a pending own

## Explicit remaining boundaries

CGI HTTPS/host metadata was **synthetic**: no TLS listener, browser or browser
cookie-policy/JavaScript/visual acceptance is claimed. The single strict
credentials-free sandboxed browser launch failed socket EPERM and was not retried
or bypassed. Declared cookie flags are not browser enforcement. Calendar/add-remove
controls and other client interactions were not exercised by that run. Manual
browser validation is delegated to the operator for this transition, not claimed
as an automated pass or used to bypass HTTPS, cookies or a sandbox restriction.

A copy to another path/inode/new disk remains unadmitted; no automatic manifest
rebind, old-key adoption or existing-data migration is implemented. Fresh NEW
installation for disposable test data does not require such migration and must
not be confused with preserving existing data. Current same-identity cold restore
is not historical-backup freshness, crash/corruption/concurrency, production-size
or human recovery acceptance. No LDAP/terminal-hardware or real deployment claim
follows. Issue30 and other full browser/operating criteria are not closed by this
source or its CI alone.

## Concrete integration and operating prerequisites

The coherent bounded Runtime/API implementation and these documentation
corrections must be reviewed and integrated together. Docker budget propagation
and strict public asset parity alone never activate a V5 Runtime. Review and
natural CI must refer to the exact aggregate source head, not only the old Draft
or a previous isolated test checkout.

A usable installation additionally needs the original NEW-only operator sequence
under one supported non-root UID and unchanged image/mount identity, a private
setup-token entry path, and a real trusted canonical HTTPS origin. The selected
V5 profile now requires a stock FileStore **non-expiring lease (0)** with a
positive wait and no per-route override. This removes lease expiry during a long
request, rather than pretending Apache/PHP timeouts prove a whole-request bound.
Normal Laravel `finally` releases it; worker exit without release intentionally
leaves it blocked until a verified-stopped, restart-excluded cleanup of that
exact store. V4 retains its original positive-lease/request-bound contract.
[Detailed lock and recovery contract](v5-nonexpiring-session-locks.md). Docker/Compose
was unavailable for our source preparation: no image/container acceptance is
implied. Follow [the existing deployment contract](installation-docker.md), not
a new bypass flag, manifest edit, Native database adoption or automatic restart.

The current public asset matches Native PR298/PR300. Its existing status-based
4xx clearing of pending events still has the separately tracked #57
uncertain-outcome gap; neither this Runtime integration nor prior successful
receipts close that issue. Disabled LDAP/sync, terminal HTTP/admin and raw
database-download capabilities require their separate complete profiles; they
are not silently enabled to obtain full URL parity. Disposable test data can use
a genuinely fresh NEW installation instead of an unimplemented cross-inode
recovery/migration operation. No further credential or deployment action is
authorized by this source preparation.
