# Local first registration in the browser — no token or terminal for the user

The user explicitly chose a local installation where **the first registered user
becomes Admin**. This is an installation policy, not identity verification based
on IP, loopback or who opens the first page. On a shared reachable network another
person could register first. Complete setup on a trusted computer/network, never
through public forwarding; do not use this mode as a public-hosting bootstrap.

## User flow

After the selected local installation has been prepared, open its configured local HTTP/HTTPS
address in the browser. Login/Register leads to the existing first-setup card:

1. Accept the prefilled `admin` name or choose another.
2. Enter email and choose/confirm your own password.
3. Register, then sign in normally.

No shared password is shipped, no token is displayed or entered, and no terminal
or separate per-browser operator approval is required. The first **successful
account transaction**, not the first page view, wins. No automatic sign-in occurs.
An iOS conversation does not itself make the installation host's localhost
reachable: the actual device or controlled browser must reach the chosen trusted
origin. No TLS warning bypass, public proxy, new host/service or actual instance
is installed by this source packet.

## Only a proven NEW local installation selects this policy

The ordinary V4 producer and older V5/native installations are unchanged until an explicit supported migration. See [the standard vacation workflow](vacation-requests-standard.md).
The existing NEW installation command's explicit `--local-browser-first-admin`
selection now creates a new random private V7 vacation-workflow directory, then certifies canonical
empty state with the existing Runtime/reference reader. Only then does it write
a private nonsecret policy file bound to that exact runtime-admission manifest.
There is no browser endpoint or target/reset command to enable this on existing
data. This installation selection is not an extra step for the registering user.
The preparer creates no password, account, setup token, key or listener.

At every setup request, FreshWeb rechecks the admitted private cohort, policy
binding and monotone closure. Setup accepts only canonical HTTP/HTTPS localhost or
`.localhost`, loopback IPv4 or RFC1918 IPv4 origins; DNS/public-name aliases do
not silently become an identity proof. Existing canonical scheme/host/port,
stock V5 non-expiring session locks, encrypted secure cookies, CSRF and persistent
setup limiter remain authoritative. The App-key must already have been prepared
through its existing authorized installation step; no key is generated by setup.
API/LDAP/terminal remain separately selected after closed first setup.

The original token profile cannot be mixed with this policy. Missing, malformed,
unbound or foreign-profile metadata fails closed. Older installations without
this new nonsecret policy file never select first-user-Admin automatically.

## One first account, then closure

The existing private operator lock serializes concurrent initial registrations.
The actual existing Runtime reader verifies that there are no users before
hashing, and `AttendanceWriter::firstLocalAdministrator` rechecks **COUNT(all
users)=0 inside its unchanged single writer transaction**. A nonempty database
never becomes a reset or privilege-upgrade path. The new row is the original
active local Admin with its original model/audit defaults. Normal anonymous
login-budget rows do not destroy initial-install provenance or lock out setup.

Only after confirmed account COMMIT is `setup-closed` written. It is never
removed, including partial closure failures. Other browsers cannot create a
second Admin or change the first one. Subsequent normal registration, when
enabled by the administrator, retains its existing ordinary-user policy.
GET does not create an account, and no chosen values are echoed/flashed.

Known field rejection precedes hashing/writing and can safely show validation
feedback. A late failure can follow a committed account or uncertain COMMIT;
it produces only generic unconfirmed feedback, no rollback claim or automatic
retry. Inspect the saved state and normal login, never reset/reopen blindly.
Keep closure in complete backups/restores; restoring an entire old empty
instance without it is not irreversible token consumption or safe recovery.

The optional local operator CLI and original token-browser workflow remain
separate alternatives, not requirements of this user-facing browser flow.

## Source-only delivery

Publication changes source, not any user's credentials or running installation.
Real installation/key creation, account submission and runtime activation still
require their applicable concrete authorization. Browser/UI acceptance is for
the user; a component/fixture proof is not actual device, TLS, deployment,
crash/recovery or existing-business-data acceptance.

One coarse disposable proof on PHP 8.5.12 / Laravel 13.38.0 uses only public
fixed dummy bcrypt/App-key values, never a hash/key generator or usable chosen
credential. Actual provider boot admits the local setup routes and V5 zero lease;
Login/Register redirect directly to the existing card. Two concurrent direct
controller requests yield one original Admin transaction, model/audits and closure.
The final Main318/319 composition is retained: open local first-user policy
refuses API/terminal/public-origin selection independently of the old token flag;
the existing physical closed-marker checks for LDAP/terminal are unchanged.
Existing-user, closed/foreign/V4/missing-policy, public-origin/HTTP and mixed-token
cases refuse, and ordinary anonymous login-budget state does not brick setup.
All owned fixtures are removed. Actual Blade in DE/EN/ZH confirms no local token
field, empty required own-password fields, preserved CSP/CSRF hooks and network
warning; the original token-mode boundary still passes. This is not an actual
HTTP/CSRF-stack, browser, TLS, Docker, configured-password hashing/login,
crash/COMMIT-loss or production recovery acceptance.
