## Real missing composition, existing components reused

Main already contains V5 generation identity, local login/enrollment/shared-budget
writers, read/business/Admin authority and own-password flow. FreshWeb still
selected V4 metadata only, its physical shared-budget provider rejected V5, and
the existing Admin controller selected intake/edit/delete only for V4. Merely
renaming isV4 would leave a false or partially mounted profile.

This packet prepares one deliberately bounded **local-only** V5 composition in
those existing classes, instead of adding a substitute runtime, wrapper,
authentication engine or credential path:

- `FreshWebConfiguration` accepts only the existing exact V4 or V5 manifest plus
  the same fixed private instance path. V5 additionally requires existing LDAP
  login off, fresh LDAP sync off, API off, and explicit shared-login-budget on.
  Unused disabled LDAP metadata remains ignored, not stat/opened. The two
  selected API/budget booleans are pinned with the existing per-request overrides,
  so later configuration drift fails `assertCurrent`. Existing private directory,
  file/manifest identity, key-format, assets, HTTPS origin, cookie/session/store,
  default-off/closure and configuration contracts remain authoritative.
- `FreshWebServiceProvider` recognizes the separate V5 Runtime metadata without
  aliasing it to isV4. Its existing private configuration and local route calls
  remain the same; no provider/default config or route option is added.
- `SharedLoginBudgetServiceProvider` accepts the explicit V5 manifest only with
  the same selected FreshWeb/read-write configuration and a V5 Runtime object.
  Its unchanged physical factory constructs a fresh Runtime from the same frozen
  manifest; no arbitrary/preloaded PDO/writer, quota fallback, key or cached
  handle is substituted. Existing LocalSession generation identity remains.
- The existing Admin intake and edit/delete selectors accept explicit V5 identity
  as well as V4. They still require their original current authority/facade,
  strict field whitelist and non-debug document. V5 gets the same existing CSP
  nonce/document policy. LDAP-specific sync/session selectors and stored LDAP
  result handling remain V4-only; enabling an intake-policy bit cannot enable a
  directory transport. The existing Blade labels the display profile truthfully
  as **V5 lokal**, and states that LDAP login/sync/API are unavailable.

The display-only page boolean is not an authority, request field or lifecycle
capability. The separate `LocalWebAccountLifecycle` interface remains unbound.
Optional correction-withdrawal/terminal/LDAP/API public selectors are not silently
broadened into a claim of complete V5 acceptance. No redesigned UI or new page.

## The actual Runtime gate still prevents any V5 route mounting

At the very beginning of `LocalWebRoutes::register`, V5 invokes the existing
immutable `RuntimeDatabase::readConnection()` with the current named configuration
and immediately disconnects any future successfully admitted connection. This is
the normal Runtime entrypoint and exact existing manifest/configuration check,
not a second opener, fake DB manager or a boolean bypass.

Today it always throws the **unchanged original V5 Runtime hold**, before the
registrar changes route/option configuration, resolves its stores or registers
any Web route. This applies to direct registrar callers as well as FreshWeb.
V4 does not perform an extra read or change its connection lifetime. Runtime's
hold body and all three original pre-open checks are entirely unchanged.

This is intentionally **not** a claim that the hold precedes every App auth/key
access: FreshWeb already format-checks its supplied App key, and existing auth
providers boot before the FreshWeb booted callback. The tested boundary is before
V5 registrar side effects and Runtime PDO opening. No secret is generated by the
new code. A future removal of the hold is a separate operating-admission decision,
not something this local profile authorizes.
